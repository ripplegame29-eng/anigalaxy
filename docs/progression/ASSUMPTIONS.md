# Допущения — RPG-прогрессия AniGalaxy

Зафиксировано на этапе 1 (разведка). Любое решение, которое принималось «сам, без ответа из ТЗ», — здесь.

## 1. Режим хранилища: `local`

Бэкенда у проекта нет и не планируется (архитектура: только `localStorage`, единственный API — прокси Kodik). По §2.2 это режим `local`:

- клиентская накрутка **технически возможна**;
- защита направлена против случайных дублей, багов и «простой накрутки» (идемпотентность, лимиты, soft-cap, реверсы, rate-limit, защита от отката часов), не против злонамеренного пользователя;
- `ServerStore` — адаптер-заглушка с тем же интерфейсом, чтобы переход на сервер не требовал переписывания движка.

Выбор — одним флагом `storageMode` в `progression.config.ts`; логики, зависящей от режима, вне адаптеров нет.

## 2. Хранилище: один документ вместо таблиц

§2.3 описывает таблицы (`user_progress`, `USER_REWARDS_LOG`, `daily_counters`, `watch_sessions`, …). В режиме `local` они реализованы **секциями одного документа** `animehub:progress:v1`:

- одна `localStorage.setItem` — атомарная запись: состояние, журнал и идемпотентные ключи не могут разойтись из-за частичной записи;
- маппинг «секция документа → таблица §2.3» описан в `docs/progression/PLAN.md` (в серверном режиме becomes таблицы 1:1).

**IndexedDB не используется**, хотя §2.2 его упоминает: весь слой сторов проекта синхронный (`useSyncExternalStore` + SSR-fallback для гидратации, см. `src/lib/store.ts`). Асинхронное хранилище сломало бы этот контракт и потребовало бы переписывания всех подписок. `ProgressStore` оставлен с асинхронным интерфейсом (`load/save/subscribe`) — локальный адаптер резолвит промисы синхронно, серверный сможет быть настоящим async без правок движка.

**Ограничение журнала:** `USER_REWARDS_LOG` хранится последние 500 записей (append-only внутри этого окна). Записи старше окна недоступны UI — это цена отсутствия сервера; при переходе на `server` журнал становится бесконечной таблицей.

## 3. Награды достижений выдаются автоматически

§9: «разблокировка идёт через движок и пишет награды в журнал». Поэтому при разблокировке XP/AC/тег/рамка начисляются сразу (вне soft-cap), UI показывает состояние «Получено», а не кнопку «Забрать».

Ручное «Забрать» осталось там, где оно уже есть и логично: **квесты** и **подарки за уровень**.

**Мостик «движок → профиль» (§12.6).** Разделы «Уведомления» и «Подарки» живут в `profile:v1`,
их пишет не движок, а `service.applySideEffects` после атомарной записи документа:

| Эффект | Что появляется в профиле |
|---|---|
| `LEVEL_UP` | уведомление «Новый уровень N! Открыта „эра: X“» + подарок (`economy.levelGiftName/Hint/Ac`, по умолчанию 50 AC) |
| `ACHIEVEMENT_UNLOCKED` | уведомление «Достижение „…“ получено (+XP, +AC)» |
| `TAG_UNLOCKED` | уведомление «Открыт тег „…“» |

Подарок начисляется в `profile.coins` (это и есть AC старой системы) и дозачитывается в
`acBalance` gain-only дельтой `meta.legacy` — при забирании вызывается `syncLegacyDelta()`,
baseline сдвигается той же записью, **повторного начисления нет**. Показ XP/AC/наград в UI
идёт из документа (`xpTotal` / `acBalance` / `progress.achievements`); `profile.xp/coins`
остаются только источником миграции и дельты, их значение в интерфейсе нигде не читается.

## 4. Миграция старых данных

| Откуда | Куда | Правило |
|---|---|---|
| `profile.xp` | `progress.xpTotal` | 1:1, без изменений |
| `profile.coins` | `progress.acBalance` | 1:1 — «монеты» прошлой системы и есть AC |
| `profile.streak`, `streakDay` | `streakCurrent` / `streakBest` | max(streak) |
| `profile.claimed` (id старых 28 достижений) | остаётся в `profile.claimed` + `progress.achievements` | id из `legacyIds` достижений конфига → `unlockedAt` момента миграции, `migrated: true`, **награда не выдаётся повторно** (старая система уже заплатила за эти релизы); id без соответствия остаются в `profile.claimed` — косметика с привязкой к старым id продолжает открываться |
| `profile.purchased`, `frameId`, `titleId`, `backgroundId` | не трогаются | владение и экипировка сохраняются |
| `history` (серии, секунды) | `counters.EPISODES_OPENED/MINUTES_WATCHED` как «открыто/проведено» | фактически досмотренные серии прошлой эпохи неизвестны (iframe) — «досмотрено» не накручивается задним числом |
| `profile.quests`/`questDay` | переролл на сегодня | незабранные квесты старого формата не являлись полученными наградами — терять нечего |
| **Уровень** | пересчитывается из XP по новой кривой §5 | XP сохранён полностью; уровень может **уменьшиться**, потому что старая кривая (60 уровней, +5 XP за уровень, максимум ≈9 300 XP) заменена на `50×L^1.2` (100 уровень ≈ 565 000 XP). Хранить «старый уровень» отдельно нельзя — уровень обязан быть функцией XP |

Миграция идемпотентна: выполняется один раз (флаг в документе), повторный запуск ничего не меняет.

## 5. Старые «титулы» (11 шт.) — отдельная категория «Подписи»

Каталог §8 фиксирует ровно 29 тегов. Старые титулы (`t-newbie`, `t-premium`, …) — другое поколение того же слота у ника, с другими именами, условиями и визуалом.

- они **не влиты** в каталог тегов, чтобы не потерять имена и не создать совпадения «тег ↔ достижение» (например, старый титул «Архивариус» = новое достижение «Архивариус» — прямое нарушение §1);
- сохранены как категория **«Подписи»** в косметике: владение, экипировка и условия открытия работают как раньше (привязка к новым id через `legacyIds`);
- в шапке профиля подпись и экипированный тег показываются рядом.

## 6. Функций, которых нет в проекте

Реализуются минимальной необходимой мерой, потому что без них не работают правила §4.1:

- **пользовательские оценки** — новое хранилище `animehub:ratings:v1`, оценка на странице тайтла, событие `TITLE_RATED` (в проекте есть только внешний рейтинг Shikimori/Kinopoisk);
- **статусы списков** — новое хранилище `animehub:statuses:v1` (`planned` «Буду смотреть», `watched` «Просмотрено»), кнопки в `TitleActions`; «Смотрю» выводится из истории. Избранное и подборки уже есть;
- **комментарии** — единый блок `CommentsBlock` работает на странице тайтла (свой стор `animehub:title-comments:v1` + демо-посев) и на стене профиля (старые данные `profile.comments`); правила `COMMENT_*` подключены к обоим (качество, cooldown, `pending` 15 минут, реверс при удалении), см. §22;
- **лайки** — мультипользовательской функции нет (один локальный аккаунт). Правила `LIKE_GIVEN`/`LIKE_RECEIVED` и семейство достижений `social` есть в конфиге с `enabled: false` — включаются одним флагом при появлении сервера. Выдавать их в локальном режиме нельзя: это была бы накрутка самому себе. Голоса 👍/👎 на комментариях — локальный декор без событий (§22).

## 7. Зачёт серии (§4.3) без доступа к плееру

Kodik — чужой iframe: позицию, процент и скорость прочитать нельзя (см. `docs/sources-1080.md`). Поэтому:

- серия засчитывается по **накопленному присутствию**: heartbeat каждые 15 с только при активной вкладке, зазор >60 с = пауза, одна активная сессия на серию;
- порог = `requiredFraction (80%)` от `duration` тайтла, если Kodik его отдал, иначе от номинала 24 мин; серии короче 5 минут не считаются эпизодом;
- перемотка в конец не помогает (нужно реально провести время у плеера), пересмотр оплаченной серии не платит (идемпотентность по `EP_COMPLETE:<title>:<episode>`).

Честное ограничение: это не защищает от «оставил вкладку открытой» — как и любой локальный режим.

## 8. Прочее

- **Тесты без зависимостей**: фреймворки не добавляются (§0.6) — юнит-тесты на встроенном `node:test`, TS компилируется существующим `tsc` во временную папку (`tools/run-tests.mjs`).
- **Админка**: `/admin/progression` существует только с бэкендом (§14). В этой сборке — dev-панель `?dev=1`, доступная только в dev-сборке, с теми же операциями и кнопками «+N к счётчику».
- **Валюта**: `profile.coins` прошлой системы = AC (курс 1:1), иначе пользователь терял бы баланс. Цены магазина пересчитаны под ориентиры §6 (рамки 300–5 000, фоны 500–3 000, теги 500–25 000); **уже купленные предметы остаются купленными** независимо от новой цены.
- **Уведомления**: глобальной системы тостов в проекте нет — добавляется своя (`lib/toasts.ts` + хост в layout), записи дублируются в раздел «Уведомления».
- **Проценты «есть у X % зрителей» не рисуются**: в режиме `local` таких данных нет (§12.2).
- **Сезоны**: в конфиге есть `seasons: []` и поддержка множителя в движке; первый сезон добавляется записью данных.
- **Premium** не даёт XP/AC и не покупается за AC — только косметика и привычные функции (AC нельзя превратить в функциональные преимущества, §1).
- **Внешние зависимости и CDN не добавляются**.

## 9. Тосты и журнал наград (§12.5–12.6)

- **Порядок монтирования**: хост `<ToastHost />` стоит в `layout.tsx` **перед** `ProgressionBoot`,
  иначе подписка встала бы уже после `SESSION_START` и первый тост (вход за день) не показался бы.
- **Состав тостов**: `XP_GAINED` (сумма + источник, при мягком капе — подпись «опыт ×0,25 до завтра»),
  `LEVEL_UP`, `ACHIEVEMENT_UNLOCKED`, `TAG_UNLOCKED`. У `AC_GAINED` и `QUEST_DONE` тостов
  **намеренно нет**: это шум — монеты и квесты и так видны в балансе и журнале.
  Лимит видимых карточек — 4, XP-тост живёт 4,2 с, остальные 7 с; первые события в одной
  пачке (вход → уровень → достижения) укладываются в лимит.
- **Дублирование**: каждая награда пишется и в «Уведомления» (через мостик `addNotice`,
  §3), поэтому тост — временный слой поверх того, что уже сохранено.
- **Журнал — модалка, а не раздел меню**: «История XP и AC» открывается кнопкой из карточки
  уровня (`ProfileDialogKind = "rewards"`), чтобы не ломать счётчики пунктов
  «боковое меню: 13» и «дропдаун: все 12». Источник — `USER_REWARDS_LOG` документа,
  итоги считаются из записей (получено XP/AC, потрачено AC), стор `profile.xp/coins` не читается.
- **Видимость тега**: чип в шапке профиля, строка в выпадающем меню, капсула у имени в
  комментариях, превью «Как видят другие». Текстовые чипы стилизованы `text-transform: uppercase`
  — проверки в CDP-скриптах сверяют текст без учёта регистра.

## 10. Dev-панель вместо админки (§14)

- **Где живёт**: `src/components/progression/DevPanel.tsx`, подключён в `layout.tsx`.
  Условие показа — `process.env.NODE_ENV === "development"` **и** `?dev=1` в адресе:
  в продакшен-сборке условие инлайнится в `false`, компонент в бандл не попадает
  (проверяется сценарием: `prod/profile?dev=1` → панели нет). Без параметра панель
  исчезает и при клиентской навигации (`popstate`-подписка, `useSyncExternalStore`).
- **Операции** — те же, что в `/admin/progression`: «+N к счётчику» (`DEV_ADJUST`),
  выдача/изъятие XP и AC с причиной (`ADMIN_GRANT`, запись источника `ADMIN`),
  выдача тега (`DEV_TAG_GRANTED` — добавлено событие: та же дорога `grantTag`,
  что у уровней и достижений), просмотр `USER_REWARDS_LOG` и ближайших достижений.
- **Всё идёт через `emit()`**: панель минует ограничения UI, но не движок —
  идемпотентность, клампы, журнал и антиабьюз (rate-limit/откат часов) сохраняются;
  повторная выдачка того же тега уходит в `rejected` (`tag_not_grantable`).
- **`?dev=1` сам по себе ничего не начисляет**: панель — только инструмент наблюдения
  и накрутки в dev-сборке; в production её нет, как и бэкенда для серверных наград.

## 11. Балансовая модель симулятора (§5, §16)

- **Почему «закрытая» формула.** Наивный метрический сим (реальные пороги достижений,
  начисляемые по мере их достижения) даёт regular L50 ≈ 265 дней — вне коридора
  [411, 685] §5. Коридоры §5 арифметически совпадают с `XP / rate`, то есть требуют,
  чтобы одноразовые награды достижений приходились преимущественно на **поздние**
  пороги. Принята модель:
  `days(L) = (xpForLevel(L) − пул × p^shape) / xpPerDay`.
- **Пул и форма.** Пул = сумма `reward.xp` всех включённых достижений (199 150 XP;
  68 из 71 — три требуют серверного режима), `p = xpForLevel(L) / xpForLevel(100)`,
  `shape = 1.6` (`sim.achievementShape`). Большие награды сидят на поздних порогах
  (1000–2000 серий, 365 дней/серий, 500 оценок, 10 000 минут), поэтому к середине
  пути накоплено меньше половины пула — и все шесть коридоров §5 проходят с запасом.
- **Всё в данных.** Профили (90/220/600 XP в сутки), цели по §5, допуск ±25% и форма
  лежат в блоке `sim` конфига; `tools/balance-sim.mjs` не хранит балансовых чисел,
  берёт кривую из движка и падает с кодом = числу провалов.
- **Границы модели**: средний темп без сезонных множителей и покупок; soft-cap в
  модели не срабатывает (все профили ≤ `softCap.dailyXp` = 1000) — это проверяется
  отдельной строкой инструмента.

## 12. Контраст AA, режим «экономия», полировка (§11, §15.8)

- **Сплошные заливки под белым текстом** (`bg-accent text-white` в активных вкладках,
  пилюлях, бейджах) давали 3.94:1 — ниже AA для мелкого текста. Введён производный
  токен `--color-accent-deep: color-mix(in oklab, var(--color-accent) 86%, black)`,
  применяется **только** там, где текст белый. Исходные `--color-accent: #1f7bff` и
  `--color-accent-2: #00c8ff` (их наличие проверяет verify6) не тронуты: они работают
  в градиентах, свечениях и как акцентный текст на тёмном фоне (4.6:1 / 9.3:1).
- **Фирменные кнопки-градиенты** (`.btn-primary`, `.btn-login`, `.btn-auth-submit`):
  белый текст на `#1f7bff → #00c8ff` даёт меньше 4.5:1 для мелкого текста. Это
  требование бренда («кнопки голубой градиент»), поэтому градиент оставлен; замер
  контраста покрывает `background-color` и худший стоп `background-clip:text`,
  но не оценивает фоновые градиенты кнопок — задокументировано в REPORT §8.
- **Футер**: `text-muted/70` (3.99:1) → `text-muted/85` — проходит AA.
- **Замер** — CDP-скрипт `prog_stage8b.mjs`: композит alpha-слоёв фона до непрозрачного
  предка, парсер `rgb/hsl/oklab/oklch/lab/lch/color(srgb)`, порог 4.5 (3.0 для
  ≥24 px или ≥18.66 px bold), градиентный текст — по худшему стопу. Итог: 0 нарушений
  на всех замерах: главная 538, профиль 99, модалка настроек 113 и 121 во вкладке
  «Внешний вид», страница тайтла 196.
- **Режим «экономия»** — `src/lib/eco.ts` + `<EcoBoot/>` в `layout.tsx`: «Авто»
  включает его при `navigator.hardwareConcurrency ≤ 4`, ручной выбор
  (Авто/Всегда/Выкл во «Внешнем виде» настроек) переопределяет автоматику и хранится
  в `animehub:eco:v1`; применяется как `<html data-eco="on">` после гидратации и гасит
  анимации/переходы тем же CSS-правилом, что и `prefers-reduced-motion`. Выбор
  переживает перезагрузку, ручной режим важнее ядра (проверяется сценарием
  `prog_stage8.mjs` с подменённым `hardwareConcurrency`).

## 13. FIX_TAGS: единая капсула `ag-tag` (§1–§5 задания)

- **Фон капсулы — формула эталона.** Прежняя подложка (`--c2` 62% на почти чёрном
  плюс радиальный `--c` 34%) давала на трёх светлых палитрах («Бог аниме»
  `#fff7ae/#00c8ff`, «Иммунный», «Император») контраст белого текста 2.79–3.47:1 —
  ниже AA. Принят фон из `reference/titles.html` (`.pill`):
  `linear-gradient(135deg, color-mix(--c 24%, #0b0b13), color-mix(--c2 20%, #0b0b13))`,
  поверх — радиальный акцент `--c` **24%** (в эталоне его нет, но он нужен для
  «живого» перелива). Худший случай по всем 29 палитрам — **5.11:1**; считает и
  держит юнит-тест `config-data.test.mjs` («белый текст капсулы даёт контраст AA»),
  и CDP-прогон `prog_tags`.
- **Текст белый (`#fff`), а не цвет `--c`, как в эталоне.** Эталон красит текст в
  цвет тега; для наших тёмных палитр это рискованно, а `#fff` + свечение даёт
  измеримую величину для AA. Свечение (`txt-neon/metal/glitch/tremor`) — это тени
  текста, они в расчёт контраста не входят.
- **Частицы: 16 у MYTHIC, 8 у SECRET.** §4 для MYTHIC называет 18, но юнит-тест
  требует `particleBudget ≤ 16` (та же граница, что у медалей). Конфликт разрешён
  в пользу 16: две «искры» на капсуле визуально неотличимы. SECRET получил собственный
  бюджет 8 (в floor входит `glitch`, а не только искры).
- **`icon` на RARE — про анимацию, а не про наличие.** Иконка нарисована у всех
  29 тегов (разметка §1 эталона), эффект `icon` добавляет ей дыхание. Отличие
  COMMON↔RARE по «иконке» = поведение слоя, не присутствие.
- **Пульс — отдельный слой `.ag-glow`.** Анимация `box-shadow` на корне перекрашивала
  капсулу каждый кадр: на `/dev/tags` (123 капсулы) это 15 длинных задач и 1445 мс

- **`perf-lite` и `<html data-eco="on">` гасят анимации корня, а не только детей** —
  иначе `fx-pulse` продолжал работать в режиме «экономии» (поймано прогоном
  `prog_tags`, починено тем же правилом).
- **Размеры**: `sm` 11 px (высота 31), `md` 13 px (42 — шапка профиля, §2 требует

## §18. Онлайн-чат (локальная симуляция)

- **Сервера нет — и это проговорено в UI**: подпись в подвале панели и в
  `README`-секции отчёта. Чат — локальная демонстрация, не сетевой продукт.
- **Хранилище одно на браузер** (`animehub:chat:v1`), синхронизация — только
  между вкладками через событие `storage`. Сообщения других «пользователей»
  генерируются тем же кодом, что и свои.
- **Боты — участники из конфига прогрессии**: у каждого ник и один из 29
  тегов, чтобы в потоке была та же капсула `ag-tag`, что и у игроков.
- **Тайминги** (18–48 с между репликами, ответ 45 % через 2.5–7 с) выбраны
  так, чтобы панель выглядела живой, но бейдж не рос бесконечно; цикл один
  на вкладку (сторож-синглтон), при закрытии панели — не останавливается
  (счётчик непрочитанных должен расти).
- **Панель — `complementary`, а не `dialog`**: иначе все чек-скрипты
  (`[role="dialog"]` для модалок) ловили бы чат вместо витрины. Модальные
  окна проекта остались нетронутыми.
- **Писать можно только вошедшему**: гость видит поток, поле ввода заменено
  подсказкой (как на референсе — там вход через аккаунт).

## §19. Вход через Telegram (демо-кнопка без бота)

- **Настоящий Login Widget требует токен бота и бэкенд**: подпись `hash`
  вычисляется секретом бота от `initData`, проверить её на клиенте без
  сервера нельзя. Выбран вариант «демо-кнопка без бота» — кнопка выглядит
  и ведёт себя как настоящий вход, но подпись не проверяется.
- **Это честно подписано в UI**: кнопка помечена бейджем «демо», панель
  выбора аккаунта подписана «демо-вход» и «без бота: аккаунт создаётся
  локально». Никаких запросов в Telegram не уходит.
- **Демо-аккаунты — три штуке из конфига** (`TELEGRAM_DEMO_ACCOUNTS` в
  `lib/auth.ts`): выбор создаёт/переключает обычный локальный аккаунт той же
  функцией, что и регистрация (`saveAccount`), с email вида `name@t.me`.
  Никнейм проходит штатную валидацию (`validateNickname`).
- **Premium сохраняется** при входе через Telegram: сменился способ входа,
  а не человек — `premiumUntil` переносится со старого аккаунта (свежая
  регистрация, наоборот, начинается без подписки — как и раньше).
- Наличие аккаунта в localStorage = «вошли» (сессий нет с самого начала
  проекта), поэтому демо-вход — это ровно «зарегистрироваться без пароля».

## §20. Локальная «база данных» + бэкапы

- Выбран вариант «Локальная БД + бэкапы»: серверной базы нет, всё хранится
  в localStorage с ключами `animehub:*` (версии и миграции — как раньше),
  защита от потери — экспорт/импорт файла и откат.
- **Экспорт** (`lib/backup.ts`) собирает все ключи проекта в один JSON
  (`anigalaxy-backup-YYYY-MM-DD.json`): метка `format`, `version`,
  `exportedAt`, сырые значения ключей как есть.
- **Импорт валидируется целиком ДО записи** (метка формата, версия не новее
  поддерживаемой, только ключи `animehub:*`, значения-строки); затем план
  восстановления: сначала запись всех данных файла, потом удаление лишних
  ключей — при сбое чтения старые данные остаются на месте.
- **Восстановление — точная копия файла**: ключи, которых нет в бэкапе,
  удаляются (иначе «откат к бэкапу» не был бы восстановлением).
- **Откат**: перед импортом текущее состояние снимается в
  `animehub:backup:preimport:v1` (сам снимок в файлы бэкапа не попадает и
  при импорте не удаляется) — кнопка «Откатить последний импорт» возвращает
  всё назад и убирает снимок.
- После импорта страница перезагружается: все сторы читают localStorage на
  старте, других «хуков обновления» у них нет.
- Лимит файла при импорте — 8 МБ (защита от случайного выбора чужого
  файла); место в хранилище проверяется на запись, нехватка — понятная
  ошибка, а не молчаливая поломка.
- Тесты: `tests/progression/backup.test.mjs` — чистое ядро
  (`buildBackup`/`validateBackup`/`parseBackup`/`planRestore`) без браузера.

## §23. Апскейл Kodik: Element Capture (допущения и пределы)

Источник: <дословно «я просто жму кнопку и там автоматически качество
лучше становится» — iframe остаётся на месте, апскейл средствами самой
страницы>.

- **Физический предел**: страница не читает пиксели кросс-доменного
  iframe (tainted canvas), SVG `url(#…)`-фильтры браузер к таким кадрам
  вообще не применяет (замеры 0/255). Единственный веб-путь, работающий
  как расширение, — Screen Capture API: `getDisplayMedia`
  (`preferCurrentTab`, одно подтверждение браузера — честнее, чем право
  расширения) + `RestrictionTarget.fromElement(iframe)` →
  `track.restrictTo()`: поток превращается в захват ТОЛЬКО пикселей
  нашего iframe (Element Capture, Chrome 132+; `restrictTo` живёт на
  `BrowserCaptureMediaStreamTrack` — проверка по базовому прототипу
  `MediaStreamTrack.prototype` остаётся запасным путём).
- **Оверлей не заменяет плеер**: канвас непрозрачный, `pointer-events:
  none` — клики, звук, управление и фулскрин остаются у Kodik. В
  фулскрине канвас не виден → кадры не рисуем (`shouldRender`), при
  скрытой вкладке — тоже. Смена серии пере-направляет `restrictTo` на
  новый iframe без повторного вопроса браузера.
- **Grace-таймеры**: плеер исчез (смена роута) — захват держим ещё 6 с
  (StrictMode успевает пере-зарегистрироваться); качество ушло с
  «Апскейл» — захват останавливаем через 20 с, чтобы шторка «идёт
  трансляция» не висела зря; включение снова в этот период — без
  повторного вопроса.
- **Деградация без потери функциональности**: отказ в разрешении, не та
  вкладка, потеря `restrictTo`, отсутствие API, нет WebGL, потеря
  контекста — всё ведёт на CSS-путь (`QUALITY_FILTERS` на iframe),
  канвас гасится, статусы честные (`denied`/`unsupported`/`idle`),
  подпись «Захват кадров недоступен — контраст и цвет остаются».
- **E2E-методика** (`verify_upscale_cdp.mjs`): скриншоты
  `Page.captureScreenshot` с `clip` в документных координатах; для
  пиксельных замеров — пауза видео кликом по центру (канвас
  `pointer-events:none`), решение о паузе по движению чипа
  (`chipMotion < 1.5`); проверки CSS-фильтров — только поллинг
  `waitFor`/`waitForFilter`: `transition-[filter] 500ms` под нагрузкой
  не укладывается в фиксированный sleep.

## §24. Anime4K в конвейере апскейла

Источник: <https://github.com/bloc97/Anime4K> (MIT, bloc97) —
дословно «тебе надо это интегрировать, чтобы работало».

- **Что интегрировано**: настоящие CNN-шейдеры Anime4K, а не наше
  приближение. Движок `lib/anime4k.ts` разбирает исходники в формате
  пользовательских шейдеров mpv (директивы `//!DESC`, `//!BIND`,
  `//!SAVE`, `//!WIDTH`, `//!HEIGHT`) и исполняет проходы на WebGL 1.
  Тексты в `lib/anime4k-shaders.ts` — дословная копия пресетов
  `Anime4K_Restore_CNN_S` (4 прохода, восстановление линий на 1×) и
  `Anime4K_Upscale_CNN_x2_S` (4 свёртки + depth-to-space в 2×) вместе
  с текстом лицензии: MIT требует сохранять уведомление о copyright.
- **Упрощения относительно mpv** (намеренные): `//!WHEN` не вычисляется —
  в mpv оно читает OUTPUT (экран) и пропускает апскейл, когда экран
  почти равен кадру; наш конвейер всегда рендерит промежуточную стадию
  2×, то есть OUTPUT/MAIN = 2.0 > 1.2 и условие истинно по построению.
  `//!OFFSET` и `//!COMPONENTS` игнорируются: проход рисует весь кадр,
  формат текстуры всегда RGBA.
- **`//!SAVE MAIN` и ping-pong**: читать и писать одну текстуру в WebGL
  нельзя — у каждого имени два слота-текстуры, а «MAIN» каждого кадра
  начинается с flip-прохода (DOM-текстура сверху вниз → FBO снизу
  вверх, та же конвенция, что у FRAG_UP).
- **Полный путь кадра**: загрузка → flip → Restore (4) → Upscale (5,
  выход 2×) → FRAG_DOWN (box-уменьшение + нерезкая маска с локальным
  клампом) → канвас. Какой движок отработал кадр, видно в
  `canvas[data-upscale-engine]` = `anime4k` | `catmull` (проверяется E2E).
- **Деградация**: сбой компиляции CNN на слабом GPU (unrolled-код
  длинный) или аллокации → `createAnime4K()`/`run()` возвращают null,
  рендерер остаётся на прежнем Catmull-Rom-пути; оба пути держат один
  и тот же контракт `UpscaleRenderer`.
- Проверки: юниты 114, линт — ровно базлайн 5 ошибок, `tsc --noEmit`
  чисто, сборка OK, E2E `verify_upscale_cdp.mjs` (57 проверок, включая
  активацию движка Anime4K).
